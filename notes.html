What We Built
The one-line answer

Synora is a responsive, themeable web project for a student productivity app: a landing page plus a working sign-up and sign-in flow, written in plain HTML, CSS and JavaScript.

  • No frameworks — no Bootstrap, no Tailwind, no React. Every style is ours.
  • No build step — open index.html in a browser and it runs.
  • One design-token file drives every colour, size and spacing value on every page.
  • Light and dark themes from the same markup, swapped by one HTML attribute.
  • The landing page is interactive without JavaScript — the mobile menu and the FAQ accordion are pure CSS/HTML.
  • The auth pages do use JavaScript, because validation and storing an account genuinely need it.
i
Say this split clearly in the viva. The landing page has one script (the theme toggle). The app's sign-up and login pages add a second (auth.js). We used JavaScript where it was necessary, not everywhere.

The design idea worth saying out loud: a page built from only one colour plus grey looks flat. Sage carries action, taupe carries information, ink carries structure. Three jobs, three colours — that is what stops it looking dull.

Contrast, and why some values were adjusted

Taupe #B09F95 is too light to read as small text on white, so the token --color-accent is a darkened #9C8A7F for text, while --color-accent-bright: #B09F95 is kept for fills (dots, gradients) where contrast does not matter. Slate is never used for body text for the same reason.

HTML — Document Structure & <head>
Every line of our <head>, explained
<!DOCTYPE html>
<!-- Tells the browser to use standards mode, not "quirks mode" -->

<html lang="en">
<!-- lang helps screen readers pronounce text and helps search engines -->

<meta charset="UTF-8">
<!-- Character encoding. Without it, characters like — and · break -->

<meta name="viewport" content="width=device-width, initial-scale=1">
<!-- Makes the page use the real device width. Without it a phone
     pretends to be 980px wide and zooms out — media queries misfire -->

<meta name="description" content="Synora brings your tasks...">
<!-- The grey text under the title in Google results -->

<meta name="color-scheme" content="light dark">
<!-- Tells the browser we support both, so scrollbars and form
     controls are drawn in the matching colours -->

<link rel="icon" href="./assets/favicon.svg" type="image/svg+xml">
<!-- Browser tab icon. SVG so it stays sharp at any size -->

<link rel="preconnect" href="https://fonts.gstatic.com" crossorigin>
<!-- Opens the network connection early so the font arrives sooner -->

<link rel="stylesheet" href="./styles/tokens.css">
<link rel="stylesheet" href="./styles/base.css">
<link rel="stylesheet" href="./styles/landing.css">
<!-- Three external stylesheets, in dependency order -->

<script src="./scripts/theme.js"></script>
<!-- NO defer here, deliberately. See the callout below -->
!
Why is theme.js the one script without defer? It must run before the browser paints anything. If it ran late, a dark-mode user would see a white flash and then the page would turn dark. This is called FOUC — Flash Of Unstyled Content. Blocking for a few milliseconds is the correct trade here.

Why semantic tags instead of <div>
  • Screen readers can jump straight to <main> or list all <nav> landmarks
  • Search engines weigh content inside <main> higher than a sidebar
  • Readability — a wall of <div> tells the next developer nothing
  • A <div> is still correct when the grouping is purely visual, e.g. .hero-visual
i
Rule of thumb we followed: if it has a meaning, use the tag; if it only has a look, use a div.

HTML — <details> and <summary>
The FAQ accordion, with zero JavaScript

<details> is a built-in HTML5 disclosure widget. The browser itself handles opening and closing, keyboard support, and screen-reader announcements.

<details class="faq-item">
  <summary>
    Do I need an account?
    <svg ...chevron... />
  </summary>
  <div class="faq-answer">
    <p>Yes. Synora is built around your account...</p>
  </div>
</details>

How we style it

/* base.css — remove the browser's default triangle */
summary { cursor: pointer; list-style: none; }
summary::-webkit-details-marker { display: none; }

/* landing.css — the browser adds/removes the `open` attribute
   for us, so we can style the expanded state with CSS alone */
.faq-item[open] { border-color: var(--color-brand); }
.faq-item[open] > summary svg { transform: rotate(180deg); }
+
Key exam point: [open] is an attribute selector. The browser writes open onto the <details> element when it expands, and CSS reacts to it. This is the whole trick — state lives in the HTML, styling reacts to it.

HTML — The One Form Input on the Page
A checkbox used as a switch, not as a form field
<input class="nav-checkbox" type="checkbox" id="nav-open"
       aria-label="Toggle navigation menu">

<!-- ...later, the visible button -->
<label class="icon-btn nav-toggle" for="nav-open">
  <svg class="icon-menu" ...></svg>
  <svg class="icon-close" ...></svg>
</label>
  • type="checkbox" — a control with two states the browser tracks for us
  • id="nav-open" + for="nav-open" — this pairing is what makes clicking the label toggle the checkbox
  • The checkbox is hidden with a 1px transparent box, not display:none, so it stays focusable with the Tab key
  • aria-label gives it a spoken name, since there is no visible text
*
The <label for> ↔ <input id> relationship is standard forms knowledge — it is normally used to make "Username:" clickable. We are using the same mechanism for a completely different purpose. Examiners like this answer.
HTML — Inline SVG Icons
No icon font, no image files

Every icon on the page is an inline <svg> written directly in the HTML.

<svg width="20" height="20" viewBox="0 0 24 24"
     fill="none" stroke="currentColor" stroke-width="1.5"
     stroke-linecap="round" aria-hidden="true">
  <path d="m9 11 3 3L22 4"></path>
</svg>
AttributeMeaning
viewBox="0 0 24 24"The internal coordinate grid. Drawing is done on a 24×24 canvas, then scaled to whatever width/height says — so it never blurs.
stroke="currentColor"The important one. The icon takes the CSS color of its parent. That is how one SVG turns sage in light mode and pale green in dark mode with no extra code.
fill="none"Outline style, not solid
aria-hidden="true"Decorative — hide it from screen readers so they don't read gibberish
+
Why inline SVG beats an icon font (like Font Awesome): no extra network request, no CDN dependency, it works offline, it is styleable with plain CSS, and it stays crisp on every screen.

CSS — Custom Properties (Design Tokens)
The single most important idea in this project

A CSS custom property (also called a CSS variable) is a value you declare once and reuse everywhere. Declared with two dashes, read with var().

/* tokens.css — declared on :root, which IS the <html> element */
:root {
  --color-brand: #53655C;
  --color-bg: #FAF9F7;
  --space-24: 24px;
  --radius-lg: 16px;
  --duration-fast: 140ms;
}

/* landing.css — used */
.btn--primary {
  background-color: var(--color-brand);
  border-radius: var(--radius-lg);
  padding: var(--space-24);
}

Why they matter here

  • Dark mode becomes trivial — redefine the same names under [data-theme="dark"] and every component updates
  • Consistency — impossible to accidentally use 23px when the scale says 24px
  • They cascade and inherit, unlike Sass variables which are compiled away
  • Readable at runtime — DevTools shows the variable name, not just a hex code

A local variable, set from HTML

Custom properties can also be set inline and read by CSS — we use this for task priority colours.

<!-- index.html -->
<div class="task" style="--color-status: var(--status-high)">

/* landing.css — the same rule serves every priority */
.task          { border-left: 3px solid var(--color-status); }
.task__tag::before { background-color: var(--color-status); }
*
Without this we would need .task--high, .task--medium, .task--done classes each repeating the same three properties. One variable replaces three classes.

CSS — Position & Stacking
The sticky header
.site-header {
  position: sticky;
  top: 0;
  z-index: 50;
  backdrop-filter: blur(12px);
}
  • sticky = behaves like relative until it hits top: 0, then acts like fixed
  • top: 0 is required — sticky does nothing without an offset
  • z-index: 50 keeps it above the page content
  • backdrop-filter: blur() blurs whatever scrolls behind the header — the frosted-glass look
The floating hero card
.hero-visual { position: relative; }

.hero-card {
  position: absolute;
  right: calc(var(--space-24) * -1);
  bottom: 0;
  width: min(19rem, 78%);
}
  • An absolute child positions against its nearest relative ancestor
  • Negative right makes it hang outside the photo — the overlap effect
  • min(19rem, 78%) = "19rem, but never more than 78% of the parent"
  • On mobile it becomes position: static and simply stacks below

The hover accent bar — animating a pseudo-element

.card::before {
  content: "";                /* mandatory */
  position: absolute;
  inset: 0 auto auto 0;     /* top:0 right:auto bottom:auto left:0 */
  width: 100%;
  height: 3px;
  background-image: var(--gradient-rule);
  transform: scaleX(0);       /* start collapsed */
  transform-origin: left;      /* grow from the left edge */
  transition: transform var(--duration-slow) var(--ease-out);
}
.card:hover::before { transform: scaleX(1); }
+
Animating transform instead of width is a performance point worth making: transform and opacity are handled by the GPU and do not trigger layout recalculation. Animating width, height, top or margin forces a reflow on every frame.

Photo + veil in one pseudo-element

.why::before {
  content: "";
  position: absolute; inset: 0; z-index: -1;
  background-image:
    linear-gradient(100deg, var(--ink-veil) 30%, var(--ink-veil-edge)),
    url("../assets/img/desk-evening.jpg");
  background-size: cover, cover;
  background-position: center, center;
}

Two background layers on one element, comma-separated. The first layer listed paints on top — so the gradient veil sits over the photo, keeping white text readable. Reversing the order would hide the photo completely.

CSS — Gradients, Transparency & Colour Functions
linear-gradient
/* The CTA band: sage → mid → taupe */
--gradient-brand: linear-gradient(
  135deg,
  #53655C 0%,
  #6B7D71 55%,
  #B09F95 140%
);

/* The little rule under each heading */
--gradient-rule: linear-gradient(
  90deg,
  var(--color-brand),
  var(--color-accent-bright) 60%,
  transparent
);
  • 135deg = top-left to bottom-right; 90deg = left to right
  • The percentage after a colour is its colour stop position
  • A stop beyond 100% (like 140%) means the last colour is never fully reached — it stays a hint of warmth
  • Ending in transparent gives a fade-out with no hard edge
radial-gradient
/* Page-wide wash, in tokens.css */
--gradient-page:
  radial-gradient(90rem 40rem at 12% -10%,
    rgba(83,101,92, .10), transparent 60%),
  radial-gradient(70rem 36rem at 92% 4%,
    rgba(176,159,149, .16), transparent 62%);
  • 90rem 40rem = the ellipse's width and height
  • at 12% -10% = its centre, partly above the viewport
  • Two washes: a cool sage bloom top-left, a warm taupe bloom top-right
  • Applied to body with background-attachment: fixed so it stays put while you scroll
*
This is the single change that stops the page reading as flat white. It is only ~10% opacity — barely visible on its own, obvious the moment you remove it.

CSS — Typography
Two typefaces, one job each
--font-heading: "Manrope", ui-sans-serif, system-ui, sans-serif;
--font-body:    "Inter",   ui-sans-serif, system-ui, sans-serif;

Everything after the first name is the font stack fallback: if Manrope fails to download, the browser walks the list left to right. system-ui means "whatever this OS uses" — San Francisco on Mac, Segoe UI on Windows.

Fluid type with clamp()

--text-hero: clamp(2.5rem, 5vw, 4rem);
/*                minimum   preferred  maximum */
  • Never smaller than 2.5rem, never larger than 4rem
  • In between it is 5vw — 5% of the viewport width, so it scales smoothly
  • One line replaces three font-size overrides in three media queries

JavaScript — theme.js, and Why It Exists
Why any JavaScript is needed at all

CSS can style a theme, but it cannot remember a choice between page loads. Storing and recalling the user's preference requires JavaScript. That is the one job theme.js has — and it is the only script the landing page loads.

JavaScript — Line by Line
theme.js in full
(function () {
  "use strict";

  var STORAGE_KEY = "synora-theme";
  var root = document.documentElement;   // the <html> element

  /* ---- 1. Pick the theme ---- */
  var saved = localStorage.getItem(STORAGE_KEY);
  var systemPrefersDark = window.matchMedia("(prefers-color-scheme: dark)").matches;
  var theme = saved || (systemPrefersDark ? "dark" : "light");

  root.setAttribute("data-theme", theme);

  /* ---- 2. Wire up the toggle buttons ---- */
  document.addEventListener("DOMContentLoaded", function () {
    var buttons = document.querySelectorAll("[data-theme-toggle]");

    for (var i = 0; i < buttons.length; i++) {
      buttons[i].addEventListener("click", function () {
        var next = root.getAttribute("data-theme") === "dark" ? "light" : "dark";

        root.setAttribute("data-theme", next);
        localStorage.setItem(STORAGE_KEY, next);
      });
    }
  });
})();

for (var i = 0; i < buttons.length; i++) {

We read the current state from the DOM each time instead of capturing it in a variable, so the handler is always correct no matter how many times the theme changes.

try/catch matters here because JSON.parse throws on malformed text. Without it, one bad character in localStorage would break every page that loads auth.js.

Hashing the password

function hashPassword(password) {
  var hash = 5381;                      // djb2's starting value

  for (var i = 0; i < password.length; i++) {
    hash = ((hash * 33) ^ password.charCodeAt(i)) >>> 0;
  }

  return hash.toString(16);             // store it as hex
}
  • A hash is a one-way function: the same input always gives the same output, but the output cannot be turned back into the input
  • That is why login works without storing the password — we hash what was typed and compare the two hashes
  • charCodeAt(i) gives the numeric character code; ^ is bitwise XOR
  • >>> 0 is an unsigned right-shift by zero — it forces the result back into an unsigned 32-bit integer so it never goes negative
  • toString(16) converts the number to hexadecimal
!
Be honest about this in the viva — it is a strength, not a weakness, to say it. This is a small 32-bit hash with no salt. It proves the principle (we never store the raw password) but it is not real security. A production app hashes on a server with bcrypt or Argon2. Anything stored in a browser can be read by whoever has the device, so client-only storage can never be genuinely secure.

One deliberate security choice you can point to

if (!user || user.passwordHash !== hashPassword(password)) {
  showAlert(form, "That username and password don't match an account.");
  return;
}

"No such user" and "wrong password" produce the same message on purpose. Distinguishing them would let someone test usernames one by one to discover which accounts exist — that is called user enumeration.

Viva Q&A — HTML
Q. What is semantic HTML and where did you use it?
HTML that describes the meaning of content, not its appearance. We use <header>, <nav>, <main>, <section>, <aside>, <footer>, <figure> and <time>. It helps screen readers navigate by landmark, helps search engines rank content, and makes the code readable.
Q. What does the viewport meta tag do?
<meta name="viewport" content="width=device-width, initial-scale=1"> tells the browser to lay the page out at the device's real width at 100% zoom. Without it, mobile browsers assume a ~980px wide desktop page and scale it down, so text is tiny and max-width media queries never trigger correctly.
Q. Explain <details> and <summary>.
A native HTML disclosure widget. <summary> is the always-visible label; everything else inside <details> shows only when it is expanded. The browser adds and removes an open attribute, which we style with the attribute selector [open]. It gives us click, keyboard and screen-reader support for free — our five FAQ items need no JavaScript.
Q. Why is there a checkbox in a page with no form?
It is the "checkbox hack" for the mobile menu. A checkbox is the only HTML element that stores an on/off state the browser tracks and that CSS can read, via :checked. The <label for> is the visible hamburger button; clicking it flips the hidden checkbox, and a sibling selector reveals the menu. No JavaScript needed.
Q. Why inline SVG instead of an icon font or PNGs?
Inline SVG is vector, so it stays sharp at any size and on any screen. It needs no extra HTTP request and no CDN, so the page works offline. And because we set stroke="currentColor", every icon automatically takes the colour of its parent — that is how the same markup gives sage icons in light mode and pale green in dark mode.
Q. What is a data attribute and where do you use one?
A custom attribute starting with data-, valid in HTML5 for storing your own information. We use two: data-theme on <html> holds the current theme and drives all our dark-mode CSS, and data-theme-toggle marks the buttons so JavaScript can find them with one querySelectorAll.
Q. What is a skip link?
The first focusable element on the page, hidden off-screen until focused. A keyboard or screen-reader user presses Tab once and can jump straight to #main, skipping the whole navbar. Ours is .skip-link, translated out of view with transform: translateY(-200%) and brought back on :focus-visible.
Q. What is the difference between alt="" and no alt attribute?
alt="" means "this image is decorative — skip it", and screen readers stay silent. Omitting alt entirely is an error: some readers fall back to announcing the file name. Our three content photos have descriptive alt text; icons are marked aria-hidden="true" instead.
Viva Q&A — CSS
Q. What is a CSS custom property and why use one?
A variable declared with two dashes (--color-brand: #53655C) and read with var(--color-brand). Unlike a Sass variable it is live in the browser, it inherits down the tree, and it can be changed at runtime. In Synora it is the mechanism behind the whole theme system: [data-theme="dark"] redefines the same names with dark values, and every component updates without a single component rule changing.
Q. Difference between Flexbox and Grid?
Flexbox is one-dimensional — a single row or a single column — and is content-driven: items size themselves. Grid is two-dimensional and container-driven: you define rows and columns first, then place items in them. We use Flexbox for the navbar, buttons and list rows, and Grid for the hero split, card galleries, the stats strip and the week calendar.
Q. What does minmax(0, 1fr) solve?
A 1fr grid track has an implicit minimum size of auto, which means it will not shrink below its content. One long word or a wide image can then push the column past its share and break the layout. minmax(0, 1fr) sets the true minimum to 0, so the track stays inside its bounds and content wraps or ellipses instead.
Q. Explain specificity, with an example from your code.
Specificity decides which rule wins when several target the same element. Score it as (IDs, classes/attributes/pseudo-classes, elements); higher wins, and source order only breaks a tie. In our mobile menu the panel contains both nav links and a .btn. We wrote .nav-panel ul a (0,1,2) rather than .nav-panel a (0,1,1) so the link styling is scoped to the list and cannot override the button's appearance.
Q. What is the difference between a pseudo-class and a pseudo-element?
A pseudo-class (one colon: :hover, :checked, :nth-child) selects an existing element that is in a particular state or position. A pseudo-element (two colons: ::before, ::after) creates a new sub-element that does not exist in the HTML. We use :checked to detect the open menu, and ::before to draw the step numerals, the wordmark lozenge and the card hover bar.
Q. How does position: sticky differ from fixed?
A fixed element is removed from the flow and pinned to the viewport from the start. A sticky element stays in normal flow and scrolls with the page until it reaches its offset (top: 0 for us), then behaves as fixed while its parent is still on screen. Sticky also requires an offset — without top, bottom, left or right it does nothing.
Q. What is :has()?
The relational pseudo-class — effectively CSS's parent selector. .site-header:has(.nav-checkbox:checked) matches a header that contains a checked checkbox. We use it to make the header background solid while the mobile menu is open. Before :has() this required JavaScript to add a class to the parent.
Q. How did you implement dark mode?
Every colour in the CSS is a custom property defined on :root. A second block, [data-theme="dark"], redefines the same names with dark values. theme.js sets data-theme on the <html> element and the whole page repaints. Two details matter: the brand green is lightened to #8FA697 because the original fails contrast on dark, and shadows are set to none because depth in dark UI comes from borders, not shadows.
Q. Why does theme.js load in the head without defer?
Because it must set data-theme before the first paint. With defer the script runs after HTML parsing, so a dark-mode user would see a flash of the light theme first — a FOUC. Blocking for a millisecond is the right trade-off here.
Q. What is clamp()?
clamp(minimum, preferred, maximum). Our hero heading is clamp(2.5rem, 5vw, 4rem): it scales with viewport width but never drops below 2.5rem or above 4rem. It gives fluid typography with no media queries at all.
Q. Why animate transform rather than width or top?
transform and opacity are composited on the GPU and do not trigger layout or paint. Animating width, height, top or margin forces the browser to recalculate layout on every frame, which drops frames on slower devices. Our card hover bar animates scaleX from 0 to 1 instead of animating width.
Q. How do CSS counters work?
counter-reset: step on the parent creates a counter at 0. counter-increment: step on each child adds 1. content: counter(step, decimal-leading-zero) in a ::before prints it as 01, 02, 03. The numerals are not in the HTML at all, so adding or reordering steps renumbers automatically.
Q. How did you choose your breakpoints?
By where the design breaks, not by device names. We narrow the browser until something looks wrong and set a breakpoint there. That gave us five: 1024px (the calendar aside gets too cramped), 940px (hero columns get too narrow), 860px (nav links collide with the buttons), 720px (cards need one column), and 400px (reduce container padding).
Viva Q&A — JavaScript
Q. Walk me through your JavaScript.
There is one file, theme.js, and one job: remembering the theme. It reads localStorage for a saved choice; if none exists it falls back to the OS setting via window.matchMedia("(prefers-color-scheme: dark)"); then it writes data-theme onto <html>. After DOMContentLoaded it finds every [data-theme-toggle] button and attaches a click handler that flips the attribute and saves the new value. The whole file is about 25 lines.
Q. What is an IIFE and why use one?
Immediately Invoked Function Expression — (function(){ ... })(). It defines a function and runs it at once. Everything declared inside is function-scoped, so STORAGE_KEY, root and theme never become global variables and cannot collide with anything else on the page.
Q. Why DOMContentLoaded?
The script is in <head> and runs before the body is parsed, so the toggle buttons do not exist yet — querySelectorAll would return an empty list. DOMContentLoaded fires as soon as the HTML is fully parsed. (It does not wait for images; window.onload does.)
Q. Difference between localStorage, sessionStorage and cookies?
localStorage persists until it is explicitly cleared and holds ~5–10 MB. sessionStorage is identical but is wiped when the tab closes. Cookies are limited to ~4 KB, can carry an expiry date, and are sent to the server with every HTTP request. We use localStorage because the theme should survive closing the browser and the server never needs to know about it.
Q. What does saved || (systemPrefersDark ? "dark" : "light") do?
Two things at once. The ternary picks "dark" or "light" from the OS preference. The || short-circuits: if saved holds a value it is used and the right-hand side never runs; if saved is null (nothing stored) the fallback is evaluated. It is the standard "use this, otherwise that" idiom.
Q. querySelector vs querySelectorAll vs getElementById?
getElementById takes an id only and returns one element. querySelector takes any CSS selector and returns the first match. querySelectorAll takes any CSS selector and returns a NodeList of every match — which is what we need, since there are two theme toggles.
Q. Why addEventListener instead of onclick?
onclick is a single property, so assigning a second handler overwrites the first. addEventListener can attach many handlers to the same event, lets you choose the capture or bubble phase, and can be removed later with removeEventListener. It also keeps behaviour out of the HTML.
Q. Is your theme JavaScript necessary? Could CSS not do it?
CSS alone can respond to the OS setting with @media (prefers-color-scheme: dark), but it cannot let the user override that and it cannot remember the choice for the next visit. Persistence requires storage, and storage requires JavaScript. That is precisely why it is the only script on the landing page.
Q. What does event.preventDefault() do in your form handlers?
A form's default behaviour on submit is to package the fields and send them to a server, then reload the page. We have no server — the account is stored in the browser — so preventDefault() cancels that and lets our own function handle everything. Without it the page would flash and reload and our code would never finish.
Q. How does one auth.js serve two different pages?
It looks for both form ids and only wires up the one it finds: getElementById("signup-form") returns null on the login page, so the if guard skips it, and vice versa. That guard is also what prevents a "cannot read property of null" error.
Q. Why validate with your own code when HTML5 already has required?
The browser's built-in validation shows an unstyleable grey tooltip, reports one field at a time, and cannot express rules like "this username is already taken" or "the two passwords must match". We set novalidate on the form to switch it off, then run our own checks — every invalid field is highlighted at once, in our own colours and wording. The required and minlength attributes stay in the markup because they still describe the constraints to assistive technology.
Q. Do you store passwords in plain text?
No. Each password is run through a hash function before it is saved, and login works by hashing what was typed and comparing the two hashes — the original text is never stored. That said, ours is a small 32-bit djb2 hash with no salt, so it demonstrates the principle rather than providing real security. A production system would hash on a server with bcrypt or Argon2. Anything kept in a browser can be read by whoever holds the device.
Q. Why is the login error message the same for a wrong username and a wrong password?
On purpose, to prevent user enumeration. If "no such user" and "wrong password" gave different messages, someone could try usernames one at a time and learn which accounts exist. One generic message reveals nothing.
Q. What is void element.offsetWidth doing in your code?
Forcing a reflow so an animation can replay. Removing and re-adding a class in the same tick does nothing, because the browser batches style changes and sees no net difference. Reading a layout property like offsetWidth makes it recalculate immediately, which splits the change in two and restarts the shake on the error banner.
Q. Why is the "Show password" toggle JavaScript when your menu toggle was pure CSS?
Because masking is controlled by the input's type attribute, and CSS cannot change an attribute — only read it. The mobile menu only needed a style change, which CSS can do via :checked ~. Switching type="password" to type="text" genuinely requires JavaScript.
Viva Q&A — Project & Design
Q. What is Synora and who is it for?
A student productivity web app that puts tasks, assignments, timetable, notes, CGPA and attendance in one workspace instead of six. This page is its landing page. The design goal was "calm" — one accent colour for actions, generous spacing, and nothing competing for attention.
Q. Do users need an account?
Yes. Synora is built around an account — it is what separates one person's tasks and notes from another's on a shared browser, and how the app knows what to load on return. Creating one takes only a username and a password: no email, no verification. The account and its data are stored in the browser's own localStorage on that device; nothing is uploaded to a server.
Q. Talk me through your colour palette.
Five colours with five jobs. Ink #22252B is structure — text, headings, the dark band. Sage #53655C is the brand and marks every action. Taupe #B09F95 is the warm accent: stat numbers, step numerals, the gradient tails. Slate #A3AEB1 is quiet decoration only, never body text, because it fails contrast. Mist #E5E8EB is every border. Splitting the roles like that is what keeps the page from looking monochrome.
Q. How is your CSS organised?
Five files by responsibility. tokens.css holds nothing but custom properties — the single source of truth. base.css is the reset and default element styling. components.css holds the pieces both the landing page and the auth pages need: buttons, icon buttons and form fields. landing.css and auth.css hold what is specific to those pages. That split is why signup.html can load buttons and inputs without pulling in the entire landing-page layout.
Q. Walk me through what happens when someone signs up.
The submit event fires, preventDefault() stops the page reloading, and we clear any previous errors. Then four checks run — name length, the username regex, whether that username is already taken, password length and composition, and whether the confirmation matches. If any fail, each bad field gets an is-invalid class and a banner shakes at the top. If they all pass, we hash the password, push a user object onto the synora-users array in localStorage, write a synora-session entry, and swap the form for a success panel.
Q. What happens after the user signs in? Where do they go?
They briefly see a success panel, then auth.js redirects them to app/dashboard.html — the app's command centre. The redirect target is a DASHBOARD constant at the top of auth.js, so it's a one-line change if the entry page ever moves. On the dashboard, app.js runs an auth guard: if there's no synora-session it sends you back to login, so app pages can't be opened without signing in.
Q. Is the site accessible?
We covered the main points: semantic landmarks, a skip link, a proper heading hierarchy, descriptive alt text with aria-hidden on decorative icons, a visible :focus-visible ring everywhere, colour contrast checked (which is why the taupe used for text is darkened and slate is never body text), a keyboard-operable mobile menu, and a prefers-reduced-motion block that disables animation.
Q. Where did the photographs come from?
Unsplash, which licenses its photos for free commercial and non-commercial use. We chose images whose own colours — sage green, warm wood, soft neutrals — already matched the palette, then laid a translucent sage/taupe gradient over each one so they sit inside the design rather than fighting it. They are downloaded into assets/img/ rather than hot-linked, so the page works with no internet connection. Photographers are credited in the footer.
Q. What was the hardest part?
Two things. First, making the page feel rich while using only five colours — the answer was giving each colour a distinct job and adding depth through gradients, tinted panels and one dark band rather than through more hues. Second, rebuilding the interactive pieces without JavaScript: working out that a hidden checkbox plus :checked ~ replaces a menu script, and that <details> replaces an accordion script.
Q. What would you add next?
A real backend. The whole app is built and working against localStorage; the honest next step is a server with proper accounts (salted, server-side password hashing) and a database, so a student's workspace syncs across devices instead of living in one browser. After that: real push/browser notifications, importing a timetable or syllabus, and an AI study planner. On the landing page, serving photos as WebP with <picture> and self-hosting the fonts remove the last external requests.
Q. Your site has no server — so what does "creating an account" really mean?
It means writing a user object into this browser's localStorage under synora-users, and recording who is signed in under synora-session. There is no network request and no database. The honest trade-off is the one stated on the landing page: your workspace does not follow you between browsers or devices, and clearing browser data clears it. What it buys is genuine privacy — nothing ever leaves the machine.

The App — Overview & Architecture

Beyond the landing page and auth flow, Synora is a full single-user product: a dashboard plus nine feature pages, all sharing one shell and one data layer. It is still only HTML, CSS and vanilla JavaScript — no framework, no build step.

The pages (all in app/): dashboard, tasks, calendar, notes, timetable, cgpa, attendance, achievements, notifications, settings.

The one-line architecture:

HTML (structure) → tokens.css (look) → storage.js (data)
            → app.js (shell + engines) → <page>.js (that page's behaviour)
  • storage.js — the only file that touches localStorage. Everyone else calls Synora.store.
  • app.js — builds the sidebar and topbar from a single NAV model, runs the auth guard, and provides toasts, modals, and the notifications / achievements / streak engines.
  • Each page's script waits for a synora:ready event, then renders into a placeholder element (e.g. [data-tasks-page]).
+
Why one shell in JS, not copied into every HTML file: the nav lives in one array in app.js. Add a page once, and the sidebar link, the active-state highlight and the mobile drawer all update everywhere. No page repeats the chrome.
!
A real bug we fixed — script order. Deferred scripts run with document.readyState === "interactive", and the feature scripts load after app.js. So app.js waits for DOMContentLoaded before firing synora:ready — otherwise it would fire before the pages had registered their listeners, and nothing would render. Good "tell me about a bug you hit" answer.
Data Layer & Storage

What. A single module (storage.js) that reads and writes everything through localStorage. Why. One place to serialise, one place to namespace by user, one place to handle corrupted data — so the data shape stays consistent across ten pages. How. Objects go in with JSON.stringify and come back with JSON.parse.

The keys:

Global:   synora-users      all accounts
          synora-session    { username } — who's signed in
          synora-theme      "light" | "dark"

Per user: synora:<username>:tasks         synora:<username>:notes
          synora:<username>:timetable     synora:<username>:attendance
          synora:<username>:cgpa          synora:<username>:achievements
          synora:<username>:notifications synora:<username>:profile
          synora:<username>:meta
  • Namespacing by username means two accounts on the same browser never see each other's data.
  • Safe reads — JSON.parse is wrapped in try/catch, returning a typed default so a corrupted value can't crash a page.
  • Persistence proof: add a task → refresh → it's still there, because save() writes the array back to localStorage immediately.
i
localStorage vs sessionStorage vs cookies: localStorage persists until cleared and is never sent to a server; sessionStorage dies with the tab; cookies are sent on every request. We want per-device persistence with no server, so localStorage is exactly right. Limit is ~5 MB of strings — plenty for text.
Shell — Toasts, Modals & the Guard

The shared UI in app.js:

  • Auth guard — every app page checks Synora.session.isAuthed() on boot; no session → redirect to login. You can't deep-link into the app signed out.
  • Toasts — Synora.toast.success(title, msg) drops a non-blocking message bottom-right that auto-dismisses. Used instead of alert().
  • Modals — Synora.openModal({title, content, footer}) builds a dialog with a backdrop, Escape-to-close and focus handling. Synora.confirm() wraps it in a Promise for delete confirmations.
  • Theme — the topbar toggle flips data-theme on <html> and saves it; theme.js applies it before first paint to avoid a flash.
*
Why not alert()/confirm()? They block the whole page, can't be styled, and feel like an error. Toasts and modals are the SaaS-standard replacements — and showing you chose them deliberately is a good design answer.
Tasks & Calendar

Task shape:

{ id, title, subject, description, deadline (YYYY-MM-DD),
  priority: critical|high|medium|low,
  status:   not-started|in-progress|completed,
  createdAt, completedAt }
  • CRUD — add / edit / delete / complete / reopen, all through Synora.tasks, which is reused by the Tasks page, the dashboard quick-add and the calendar.
  • Views — All, Today, Upcoming, Overdue, Completed are computed by comparing each deadline to today with a daysUntil() helper built on the Date API.
  • Search & sort — filter by title/subject text; sort by deadline, priority order, or newest.
  • Calendar integration — the calendar reads the same task store, so any task with a deadline appears on its day. One data source, two views — never two disconnected systems.
+
Priority isn't colour-only. Each badge shows a coloured dot and a word ("High"), so it still reads for colour-blind users and in greyscale. Accessibility point worth making.
CGPA Calculation

What. A credit-weighted grade average. Why. Not every subject is worth the same credits, so a plain average would be wrong. How.

CGPA = Σ(credit × grade point) / Σ(credits)

Grade letters map to points via the chosen scale (10-point Indian, or 4.0 GPA). Worked example (the sample data, 10-point scale):

DBMS               4 credits × A  (9)  = 36
Computer Networks  3 credits × A+ (10) = 30
Operating Systems  4 credits × B+ (8)  = 32
                   ----------------------
                   11 credits   98 points

CGPA = 98 / 11 = 8.91

Invalid rows (no grade, zero credits) are skipped, not counted as zero, so a half-filled table still gives a correct partial CGPA. The value updates live as you type, drives a ring, and a bar chart shows grade points per subject.

Attendance Calculation

What. Current percentage plus the two questions students actually ask. How.

attendance % = attended / total × 100

If below target — how many classes must I attend in a row to reach it? Solve (attended + n)/(total + n) ≥ target/100:

n = ceil( (target·total − 100·attended) / (100 − target) )

Example: 26/38 attended, target 75%
n = ceil((75·38 − 100·26) / (100 − 75)) = ceil(250/25) = 10
Check: (26+10)/(38+10) = 36/48 = 75%  ✓

If at/above target — how many can I safely miss? Solve attended/(total + x) ≥ target/100:

x = floor( attended·100/target − total )

Example: 34/40 attended (85%), target 75%
x = floor(34·100/75 − 40) = floor(5.33) = 5
!
Edge cases handled: zero classes held (no divide-by-zero — shows a prompt instead), a 100% target (no "can miss" is possible), and attended capped at total.
Achievements, Notifications & Streak

Three cross-cutting engines in app.js. Any data change calls Synora.refresh(), which re-runs them so badges and alerts stay in sync.

  • Achievements — each badge has a measure(context) and a goal (e.g. complete 5 tasks, reach a 3-day streak, add a timetable). When measure ≥ goal and it isn't already unlocked, it's recorded with a timestamp and announced with a toast. Nothing is a fake static badge — they all read real data.
  • Notifications — generated from data (due-today, overdue, attendance below target) plus events (achievement unlocked). Each has a stable key so the same alert is never added twice. The bell shows an unseen count.
  • Streak — completing a task on a new day increments meta.streak; a gap resets it. Only "live" if it includes today or yesterday.
*
Dedupe by key is the trick to know: without it, every page load would re-add "DBMS is due tomorrow". The key due:<taskId>:<deadline> makes it idempotent.
Viva Q&A — The Application
Q. How does data persist without a backend?
Every module reads and writes through storage.js, which serialises objects to the browser's localStorage with JSON.stringify and reads them back with JSON.parse. Add a task, refresh, and it's still there because it was written to disk immediately.
Q. Why namespace keys by username?
So two accounts on one browser stay separate. Keys look like synora:manan_07:tasks. The signed-in username comes from synora-session, and every per-user read/write is prefixed with it.
Q. What happens if localStorage is cleared?
Everything for that browser is gone — accounts and all their data — because there is no server copy. That's the honest trade-off of a frontend-only app; Settings offers a JSON export as a manual backup.
Q. How is the CGPA calculated?
Credit-weighted: Σ(credit × grade point) / Σ(credits). Grades map to points through the selected scale. For the sample data that's (4×9 + 3×10 + 4×8) / 11 = 98/11 = 8.91.
Q. How do you work out how many classes a student can miss?
Solve attended/(total + x) ≥ target/100 for x, giving x = floor(attended·100/target − total). If they're below target, I instead solve for classes to attend in a row: n = ceil((target·total − 100·attended)/(100 − target)).
Q. How do achievements unlock — are they hard-coded?
No. Each has a measure(context) that counts real data (tasks completed, streak length, notes written) against a goal. When the measure reaches the goal it's recorded with a timestamp and can't re-fire. Delete data and the count reflects it.
Q. How does the calendar relate to tasks?
It reads the same task collection. A task's deadline places it on that day; there's no separate calendar data. That's why adding a task on the calendar and on the Tasks page both show up everywhere.
Q. How is the sidebar built for every page?
app.js holds one NAV array and renders the sidebar and topbar into placeholder elements on each page. The active link is decided by document.body.dataset.page. One array is the single source of truth for navigation.
Q. Why did you replace alert() and confirm()?
They block the page, can't be styled, and read as errors. I built a toast system for feedback and a modal-based Synora.confirm() that returns a Promise for destructive actions — the same pattern real products use.
Q. How does the app stay signed-in-only?
On boot, app.js checks for a synora-session. If there isn't one, it redirects to the login page before rendering anything, so app pages can't be used while signed out.
Q. How is the app responsive?
Desktop uses a fixed sidebar; below 900px CSS turns it into an off-canvas drawer with a hamburger and a backdrop, so navigation is never lost and nothing scrolls sideways. The timetable switches from a 7-column grid to stacked day cards, and cards reflow with CSS Grid auto-fit.
Q. What was a real bug you fixed?
Deferred scripts run before DOMContentLoaded but in order, so app.js was firing its synora:ready event before the later page scripts had added their listeners — nothing rendered. Fixing it to dispatch on DOMContentLoaded made every page render. (Also an early copy-paste bug: a double-quote inside a double-quoted HTML string, caught by running node --check.)
Q. Is the password storage secure?
Honestly, no — and I'd say so. It's hashed rather than stored raw, but it's client-side, so it's obfuscation, not security. A real app hashes on a server with a salted algorithm like bcrypt. I used a client hash because there is no server and I didn't want plaintext in localStorage.
Q. How would you add a backend?
Swap the storage.js layer for fetch calls to a REST API, move accounts and hashing server-side, and put the data in a database. Because every module already goes through that one layer, the pages barely change.
Q. Why vanilla JavaScript and no framework?
The brief required it, and for a project this size it's the right call: no build step, no dependencies, it runs by opening a file, and it forces you to actually understand the DOM, events and state rather than leaning on a library. A logical sequence that shows every feature and the persistence story:

  1. Open the landing page — say the design runs off a token system with light/dark from one attribute.
  2. Create an account — show the validation (bad username, mismatched passwords), then submit. Point out the redirect to the dashboard and the auth guard.
  3. Dashboard — "this answers what's due today." Note the live counts, the progress donut, and the academic snapshot (attendance % and CGPA computed from real data).
  4. Tasks — add a task, complete one (a toast fires, the streak/achievement updates), switch views, search.
  5. Calendar — show the task on its deadline day; click the day to add another — prove it's the same data.
  6. CGPA — walk the formula on screen; change a grade and watch the ring update.
  7. Attendance — show a subject below target ("attend N in a row") and one above ("can miss N").
  8. Timetable / Notes — add a class and a note; open DevTools → Application → Local Storage to show them saved as JSON.
  9. Achievements / Notifications — show badges unlocked by what you just did, and the bell count.
  10. Refresh the page — everything is still there. Toggle dark mode. Resize to a phone width to show the drawer. Done.
