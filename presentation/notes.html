HTML5

Document structure

Every Synora page is a valid HTML5 document before a single style or script runs.

The skeleton of a page
What

HTML (HyperText Markup Language) is the structure of a web page — a tree of nested elements. HTML5 is its current version, adding semantic tags, native form types and media elements. A document declares its type, sets metadata in the <head>, and puts visible content in the <body>.

Visual
<!DOCTYPE html> html ├── head (metadata: not shown on the page) │ ├── meta charset / viewport │ ├── title │ └── link / script (CSS + JS) └── body (everything the user sees) ├── header ├── main └── footer
In Synora

The real head of index.html — note the two essential meta tags, a descriptive title and the CSS/JS wiring:

htmlfrom Synora · index.html
<!DOCTYPE html>
<html lang="en">
<head>
  <meta charset="UTF-8">
  <meta name="viewport" content="width=device-width, initial-scale=1">
  <title>Synora — One calm home for everything you're studying</title>
  <meta name="description" content="Synora brings your tasks, notes,
        timetable and grades into a single, quiet workspace.">
  <link rel="stylesheet" href="./styles/tokens.css">
  <script src="./scripts/theme.js"></script>
</head>
<body class="app" data-page="dashboard"> … </body>
</html>
Why it matters

<!DOCTYPE html> puts the browser in standards mode. charset="UTF-8" makes accented characters and symbols render correctly. The viewport meta is what makes responsive design work on phones — without it, mobile browsers pretend to be 980px wide and shrink everything.

Viva

Q: What does the viewport meta tag do?
A: It tells the browser to match the layout width to the device width, so CSS media queries and responsive layouts behave correctly on mobile.

Q: Why lang="en"?
A: It declares the document language for screen readers, search engines and spell-checkers.

Revise: DOCTYPE → html → head (metadata) + body (content). charset, viewport and title are the non-negotiable head tags.
HTML5

Semantic HTML

Tags that describe meaning, not just boxes.

Meaningful tags must know
What

Semantic elements name the role of their content: <header>, <nav>, <main>, <section>, <article>, <aside>, <footer>. The alternative — wrapping everything in <div> — works visually but tells the browser and assistive tech nothing.

Visual
<header> ── logo + primary nav <main> <section> ── a themed block of the page <article> ── a self-contained card <aside> ── side content (sidebar) <footer> ── contact, copyright
In Synora

The landing page uses a real semantic outline — <header> for the site bar, <main> for content, labelled <section> blocks, and app pages use <aside> for the sidebar:

htmlfrom Synora · index.html
<header class="site-header">
  <nav class="nav" aria-label="Primary"> … </nav>
</header>

<main id="main">
  <section class="hero" id="top"> … </section>
  <section class="section" id="features" aria-labelledby="features-title"> … </section>
</main>

App pages (dashboard, tasks…) use a shell of <aside data-sidebar> + <header data-topbar> + <main class="page">.

Why it matters

Three payoffs: readability (the markup documents itself), maintainability (a labelled section is easy to find), and accessibility (screen readers let users jump to main or between nav landmarks). SEO also leans on this structure.

Viva

Q: Difference between <section> and <div>?
A: <section> is a semantic grouping with meaning (usually a heading); <div> is a generic container with no meaning, used only for styling/scripting hooks.

Q: Can a page have more than one <nav>?
A: Yes — label each with aria-label so they are distinguishable.

Revise: Semantic = meaning. header / nav / main / section / article / aside / footer describe the role; div/span are meaningless wrappers.
HTML5

Accessibility basics

Making the interface usable by keyboard and screen reader.

Labels, alt, ARIA, focus
What

Accessibility (a11y) is building so that people using keyboards, screen readers or high-contrast modes can still operate the app. The main HTML levers: real <label>s tied to inputs, alt text on meaningful images, correct input types, semantic buttons, visible focus, and aria-* only where semantics fall short.

In Synora

Real accessibility touches from the codebase:

htmlfrom Synora · index.html
<nav class="nav" aria-label="Primary">
<input type="checkbox" id="nav-open" aria-label="Toggle navigation menu">
<button type="button" class="icon-btn theme-toggle" data-theme-toggle
        aria-label="Toggle dark mode"> … </button>
<svg … aria-hidden="true"> … </svg>   <!-- decorative icons hidden from AT -->
<img src="logo-lockup-dark.png" alt="" aria-hidden="true">

Decorative SVGs and duplicate logos carry aria-hidden="true" and empty alt=""; interactive controls that show only an icon get an aria-label. Focus styles come from a shared --focus-ring token in CSS.

Why it matters

An icon-only button with no label is silent to a screen reader. An alt="" on a decorative image stops the reader announcing a useless filename. These are cheap wins that make the difference between usable and unusable.

Be honest in the vivaSay “we applied accessibility basics — labels, aria-labels on icon buttons, aria-hidden on decorative graphics, keyboard-focusable controls.” Do not claim full WCAG AA compliance — the project wasn't audited to that bar.
Viva

Q: When do you use aria-label?
A: When a control has no visible text (e.g. an icon-only button), to give assistive tech an accessible name.

Q: Why alt="" instead of removing alt?
A: An empty alt marks the image as decorative so the screen reader skips it; a missing alt makes some readers announce the file name.

Revise: label inputs, alt on images (empty for decorative), aria-label on icon buttons, aria-hidden on decorative graphics, keep focus visible.
HTML5

Forms

How Synora collects sign-in, sign-up and setup data.

Inputs, labels, types & native validation
What

A <form> groups controls: <input>, <select>, <textarea>, <button>, each paired with a <label>. Attributes like type, required, minlength and pattern give you free browser-level validation before any JS runs.

In Synora

The sign-up form uses labelled fields and specific input types:

htmlexample · mirrors Synora signup.html
<form novalidate>
  <label class="field__label" for="email">Email</label>
  <input class="input" id="email" name="email" type="email" required>
  <p class="field__error"></p>

  <label class="field__label" for="password">Password</label>
  <input class="input" id="password" name="password" type="password" required>

  <button class="btn btn--primary" type="submit">Create account</button>
</form>

Forms appear in Sign in, Sign up, Personalize Synora (onboarding), Contact, and inside modals for creating subjects, tasks and timetable entries. Synora uses novalidate and validates in JavaScript so it can show its own styled error messages (see the Events → Form validation section).

Why it matters

type="email" and type="password" bring the right mobile keyboard and masking for free. A <label for> tied to an input's id means tapping the label focuses the field and screen readers announce it.

Viva

Q: Two ways to associate a label with an input?
A: <label for="id"> matching the input's id, or wrapping the input inside the <label>.

Q: What does novalidate do and why use it?
A: It disables the browser's built-in validation bubbles so we can run our own JS checks and render custom, styled error text.

Revise: form → label + input(type) + button. type=email/password/date/time. required for mandatory. Synora validates in JS for custom errors.
CSS3

CSS fundamentals

Selector → property → value, plus the cascade.

Rules, selectors, specificity
What

CSS (Cascading Style Sheets) controls presentation and layout. A rule targets elements with a selector and sets one or more property: value declarations.

cssexample
.btn {            /* selector */
  background: #53655C;   /* property: value */
  color: #fff;
}
Visual — how selectors compare
tag p weakest class .btn middle id #main strong inline style="…" strongest (avoid)

When two rules touch the same property, the more specific one wins; ties are broken by source order (later wins). This is the “cascade”.

In Synora

Synora styles almost everything through classes (.btn, .card, .field) and uses data- attributes for state ([data-theme="dark"]), keeping specificity low and predictable. IDs are used for anchors and single hooks, not for styling weight.

Viva

Q: class vs id?
A: A class is reusable on many elements; an id must be unique per page and has higher specificity.

Q: What is the cascade?
A: The algorithm that resolves conflicting rules by importance, specificity, then source order.

Revise: selector { property: value }. Specificity: inline > id > class > tag; later rule wins on a tie. Synora styles by class.
CSS3

Custom properties (CSS variables)

The single source of truth that makes theming possible.

Design tokens
What

A custom property is a reusable value declared with --name and read with var(--name). Declared on :root, it is available everywhere and can be overridden in a nested scope — which is exactly how dark mode works.

In Synora

Synora's whole look comes from tokens in styles/tokens.css (≈85 unique token names). A slice of the real palette:

cssfrom Synora · styles/tokens.css
:root {
  --palette-sage: #53655C;      /* brand */
  --palette-taupe: #B09F95;     /* warm accent */
  --color-bg: #FAF9F7;          /* warm paper white */
  --color-surface: #FFFFFF;
  --color-brand: #53655C;
  --color-text: #22252B;
  --radius-md: 12px;
  --space-16: 16px;
}
[data-theme="dark"] {
  --color-bg: #1A1C21;          /* same names, new values */
  --color-surface: #22252B;
  --color-text: #EDEFF1;
}
Ink #22252B Sage #53655C Slate #A3AEB1 Mist #E5E8EB Taupe #B09F95
Why it matters

Consistency (one place defines “brand green”), maintainability (change it once, it updates everywhere) and theming (redeclare the same token names under [data-theme="dark"] and the entire UI re-colours with zero component changes).

Viva

Q: Why custom properties over Sass variables?
A: They are live at runtime — the browser resolves var() on the fly, so overriding them in a scope (dark mode) instantly re-themes the page. Sass variables are compiled away before the browser sees them.

Revise: --x: value on :root, read with var(--x). Override the same names under [data-theme=dark] → instant theming.

The Box Model

Every element is a box: content, padding, border, margin.

Content · padding · border · margin
Visual
MARGIN
BORDER
PADDING
CONTENT
┌──────────── MARGIN ────────────┐ │ ┌────────── BORDER ─────────┐ │ │ │ ┌──────── PADDING ─────┐ │ │ │ │ │ ┌── CONTENT ──┐ │ │ │ │ │ │ └─────────────┘ │ │ │ │ │ └─────────────────────┘ │ │ │ └───────────────────────────┘ │ └────────────────────────────────┘
What

Content is the text/image; padding is space inside the border; border is the edge; margin is space outside, pushing neighbours away. Padding grows the clickable/coloured area; margin creates gaps.

In Synora

The real button applies padding for its tap area and a radius for its shape; cards add padding + border + shadow. Synora also sets box-sizing: border-box globally so width includes padding and border:

cssfrom Synora · styles/components.css
.btn {
  display: inline-flex;
  gap: var(--space-8);
  padding: var(--space-12) var(--space-24);   /* inside space */
  border: 1px solid transparent;
  border-radius: var(--radius-md);
}
/* global reset */
*, *::before, *::after { box-sizing: border-box; }
Why it matters

box-sizing: border-box makes layouts predictable: a width: 200px box stays 200px even after you add padding and border, instead of ballooning. Padding vs margin is the classic viva trap.

Viva

Q: padding vs margin?
A: Padding is space inside the border (part of the box's background); margin is space outside the border (transparent, separates boxes).

Q: What does box-sizing: border-box change?
A: Width/height now include padding and border, so boxes don't overflow when you add them.

Revise: Content + Padding + Border + Margin. Padding = inside, Margin = outside. border-box = width includes padding+border.
CSS3

Flexbox

One-dimensional layout — align things along a row or a column.

Main axis, cross axis, justify, align, gap must know
What

Flexbox lays items out in one dimension — a row or a column. justify-content spaces items along the main axis; align-items positions them on the cross axis; gap sets spacing between them.

Visual
MAIN AXIS → (flex-direction: row) justify-content: space-between [ Logo ] [ Nav ] [ Profile ] ↑ align-items controls the vertical (cross) axis
Live: display:flex; justify-content:space-between; gap:8px
LogoNavProfile
In Synora

Flexbox is Synora's workhorse — display:flex appears well over 100 times. The button lines up its icon and label with it:

cssfrom Synora · styles/components.css
.btn {
  display: inline-flex;
  align-items: center;      /* icon + text vertically centred */
  justify-content: center;
  gap: var(--space-8);      /* space between icon and label */
}

Also the top bar (logo · links · actions), card headers, form rows, chip clusters and the toast stack.

Why it matters

Navbars, button rows and toolbars are naturally one-dimensional. Flexbox aligns and distributes them without floats or manual margins, and gap spaces them with one line.

Viva

Q: Why Flexbox for the navbar?
A: The navbar is a single row of items — a one-dimensional layout — which is exactly what Flexbox is for.

Q: justify-content vs align-items?
A: justify-content distributes items along the main axis; align-items positions them on the cross axis.

Revise: Flexbox = ONE dimension. main axis (justify-content) + cross axis (align-items) + gap. Perfect for navbars and button rows.
CSS3

CSS Grid

Two-dimensional layout — rows and columns together.

Columns, rows, gap, auto-fit must know
What

Grid arranges items in two dimensions at once. grid-template-columns defines the column tracks; items flow into the cells; gap spaces both directions.

Visual
grid-template-columns: 1fr 1fr; ┌─────────┬─────────┐ │ A │ B │ ├─────────┼─────────┤ │ C │ D │ └─────────┴─────────┘
Live: display:grid; grid-template-columns:1fr 1fr; gap:8px
ABCD
In Synora

Grid builds the responsive card decks and the calendar. The dashboard/notes/achievement grids use auto-fit + minmax so columns reflow by themselves:

cssfrom Synora · styles/app.css
.notes-grid {
  display: grid;
  grid-template-columns: repeat(auto-fill, minmax(240px, 1fr));
  gap: var(--space-16);
}
.cal-grid {                     /* the 7-day calendar */
  display: grid;
  grid-template-columns: repeat(7, minmax(0, 1fr));
  gap: 6px;
}
Synora gotcha (real bug we hit)Use minmax(0, 1fr) not plain 1fr when a cell holds a table or long text — a bare 1fr refuses to shrink and causes horizontal overflow.
Why it matters

repeat(auto-fit, minmax(240px, 1fr)) is responsive with no media query: it fits as many 240px+ columns as the width allows and stretches them to fill. That single line handles desktop → mobile for the card decks.

Viva

Q: Why Grid for the dashboard, not Flexbox?
A: The dashboard is a two-dimensional arrangement of cards across rows and columns — Grid's job. Flexbox handles one axis at a time.

Q: What does 1fr mean?
A: One fraction of the free space — tracks split leftover space proportionally.

Revise: Grid = TWO dimensions. grid-template-columns + gap. repeat(auto-fit, minmax(240px,1fr)) = responsive with no media query.

CSS3

Responsive design & media queries

One layout that adapts from desktop to phone.

Breakpoints, fluid units, @media high
What

Responsive design means the layout adapts to the screen instead of breaking. Tools: relative units (%, rem, fr, clamp()), flexible layouts (Flex/Grid) and media queries that apply CSS only when a condition (usually viewport width) is met.

Visual
DESKTOP ▸ multi-column, sidebar visible ↓ @media (max-width: 900px) TABLET ▸ fewer columns, tighter spacing ↓ @media (max-width: 560px) MOBILE ▸ single column, collapsible menu
Syntax
cssexample
/* desktop-first: base styles are the wide layout,
   media queries scale DOWN as the screen shrinks */
.sidebar { width: 260px; }

@media (max-width: 900px) {
  .sidebar { position: fixed; transform: translateX(-100%); }
}
In Synora

The app CSS has ~23 media-query blocks with breakpoints like 1000px / 900px / 560px. Grids collapse column counts, the sidebar becomes a slide-in drawer, and spacing tightens.

cssfrom Synora · styles/app.css
@media (max-width: 900px) { … stack the app shell … }
@media (max-width: 560px) { … single-column, larger tap targets … }
@media (prefers-reduced-motion: reduce) { .loader__dots span { animation: none; } }
Be honest: Synora is desktop-firstOur breakpoints are dominated by max-width — base styles describe the desktop layout and media queries scale it down. That is desktop-first. Do not call it mobile-first (which would use min-width queries building up from a mobile base). Know the difference; state which one we used.
Mobile-first (the concept)
Base styles = mobile ↓ @media (min-width: 768px) → tablet ↓ @media (min-width: 1024px) → desktop

Mobile-first starts small and adds complexity with min-width. It's a valid strategy — Synora simply chose the opposite direction.

Viva

Q: What is a media query?
A: A CSS rule that applies styles only when a condition — usually a viewport width — is met.

Q: Is Synora mobile-first or desktop-first?
A: Desktop-first — base styles are the desktop layout and max-width queries scale it down.

Q: Why did you need responsive design?
A: Students open Synora on laptops and phones; the layout has to stay usable on both.

Revise: Responsive = layout adapts. Media query = conditional CSS. Synora = desktop-first (max-width). Mobile-first = min-width, builds up.
CSS3

Dark mode & theming

Two looks, one set of components.

The token-swap approach
What

Dark mode is not a second stylesheet. Synora keeps one set of components and swaps the token values based on a data-theme attribute on <html>. CSS reacts instantly because every colour is a var().

Visual — the flow
click toggle ↓ JS: html[data-theme] = "dark", save to localStorage ↓ CSS: [data-theme="dark"] redefines --color-bg, --color-text … ↓ every var(--…) re-resolves → whole UI recolours
In Synora

The theme contract is owned by scripts/theme.js: key synora-theme = "light" | "dark", applied as <html data-theme>. It runs synchronously in the head so a dark-mode user never sees a white flash. Full script:

jsfrom Synora · scripts/theme.js
var STORAGE_KEY = "synora-theme";
var root = document.documentElement;

// 1. Pick: saved choice, else OS preference, else light
var saved = localStorage.getItem(STORAGE_KEY);
var systemPrefersDark = window.matchMedia("(prefers-color-scheme: dark)").matches;
var theme = saved || (systemPrefersDark ? "dark" : "light");
root.setAttribute("data-theme", theme);

// 2. Toggle buttons flip and remember the choice
document.querySelectorAll("[data-theme-toggle]").forEach(function (btn) {
  btn.addEventListener("click", function () {
    var next = root.getAttribute("data-theme") === "dark" ? "light" : "dark";
    root.setAttribute("data-theme", next);
    localStorage.setItem(STORAGE_KEY, next);
  });
});

This very page uses the same idea with its own key (synora-notes-theme) and its own attribute (data-notes-theme) — try the moon icon in the top bar.

Why it matters

One component set stays visually consistent in both themes; no duplicated CSS. Reading the OS preference (matchMedia) respects the user's system choice, and saving to localStorage remembers it next visit.

Viva

Q: How does dark mode work without a second stylesheet?
A: We redefine the same CSS custom properties under [data-theme="dark"]; since components read colours via var(), flipping the attribute recolours everything.

Q: Why is theme.js loaded synchronously in the head?
A: To set the theme before first paint and avoid a flash of the wrong theme.

Revise: Dark mode = swap token values under [data-theme=dark]. JS sets the attribute + saves to localStorage; matchMedia reads the OS default.
CSS3 · UX

The loading screen

CSS animation + a little JS timing.

Splash, keyframes, reveal
What / Why UX

A loading screen covers the brief moment while scripts boot and data is read, so the user sees a calm branded splash instead of a half-built page flickering into place. It signals “we're working” and smooths the entry.

Visual — the flow
open page ↓ full-screen loader painted (CSS) ↓ dots pulse via @keyframes ↓ JS: add .is-hidden → CSS fades opacity ↓ JS: loader.remove() → page revealed
In Synora — the CSS

The animation is pure CSS; three dots pulse on a stagger and the whole overlay transitions its opacity:

cssfrom Synora · styles/app.css
.loader { position: fixed; inset: 0; display: grid; place-content: center;
          transition: opacity var(--duration-slow) var(--ease-out); }
.loader.is-hidden { opacity: 0; visibility: hidden; }
.loader__dots span { animation: loader-pulse 1s var(--ease-out) infinite; }
.loader__dots span:nth-child(2) { animation-delay: 0.15s; }
.loader__dots span:nth-child(3) { animation-delay: 0.3s; }
@keyframes loader-pulse {
  0%, 100% { opacity: .25; transform: translateY(0); }
  50%      { opacity: 1;   transform: translateY(-4px); }
}
@media (prefers-reduced-motion: reduce) { .loader__dots span { animation: none; } }
In Synora — the JS

JavaScript only handles timing and removal — it toggles the class, then removes the node after the fade:

jsfrom Synora · scripts/dashboard.js
function hideLoader() {
  var loader = document.getElementById("app-loader");
  if (!loader) return;
  loader.classList.add("is-hidden");                 // CSS fades it out
  window.setTimeout(function () { loader.remove(); }, 400); // then remove
}
Viva

Q: Is the loader animation JavaScript?
A: No — the animation is CSS @keyframes and a CSS transition. JavaScript only toggles a class and removes the element after the fade.

Q: Why a minimum display time?
A: So the splash doesn't flash-and-vanish on a fast load, which looks like a glitch.

Honest scopeSay “CSS does the animation; JS controls the timing and removal.” Don't claim JS animates the dots — it doesn't.
Revise: Loader = CSS @keyframes + opacity transition. JS = add .is-hidden, then loader.remove(). Reduced-motion disables the pulse.

Variables — let, const, var

Naming values so logic can use them.

const means the binding is fixed; an object held by a const can still have its properties changed.

In Synora

Synora's scripts predate a strict ES6 style and lean on var with IIFE module wrappers, but the concepts are identical. Real lines from the CGPA calculator:

jsfrom Synora · scripts/app.js
var totalCredits = 0, weighted = 0;   // will change → mutable

A modern equivalent for a fixed value would be const STORAGE_KEY = "synora-theme"; — a name that must never be reassigned.

Viva

Q: let vs const?
A: Both are block-scoped; let can be reassigned, const cannot. Prefer const unless you need to reassign.

Q: Can you change a const object?
A: Yes — you can mutate its properties; you just can't point the const at a new object.

Revise: const by default, let when it changes, avoid var. const = fixed binding (object contents can still change).
JavaScript

Data types

The kinds of values JavaScript stores.

string · number · boolean · null · undefined · object · array
What

Primitives: string, number, boolean, null, undefined (and symbol/bigint). Everything else is an object — including arrays and functions.

In Synora — all in one record
jsexample · shape of Synora data
var subject = {
  id: "sub_04",              // string
  name: "OOPS",              // string
  credits: 4,                // number
  trackAttendance: true      // boolean
};
var lastCompletionDate = null;   // null  — nothing recorded yet
var maybeUser;                   // undefined — declared, no value
var subjects = [subject];        // array (an object)
null vs undefined

undefined = the variable exists but was never given a value. null = an intentional “empty on purpose”. Synora uses null deliberately, e.g. lastCompletionDate: null and “return null if nothing is gradeable yet”.

Viva

Q: Is an array a type?
A: It's an object — typeof [] is "object". Use Array.isArray() to check.

Q: typeof null?
A: "object" — a long-standing JavaScript quirk.

Revise: string, number, boolean, null, undefined are primitives; array & object are objects. null = intentional empty, undefined = no value yet.
JavaScript

Functions & arrow functions

Reusable blocks of logic.

Declaration, parameters, return, arrows
What

A function packages logic you can call by name, passing arguments into its parameters and getting a return value back. Arrow functions are a shorter syntax, common as callbacks.

jsexample
function attendancePct(attended, held) {   // declaration
  if (held === 0) return 0;                // guard
  return (attended / held) * 100;          // return value
}
const add = (a, b) => a + b;               // arrow function
In Synora

Synora is built from small named functions plus arrow callbacks. Real examples — a helper and an arrow callback used to remove a toast when its animation ends:

jsfrom Synora · scripts/app.js & storage.js
function gradePoint(grade) { … return the 10-point value for a grade … }

Propagation — bubbling & capturing

How an event travels through the tree.

Capturing down · target · bubbling up
Visual
CAPTURING (phase 1) BUBBLING (phase 3) document button (target, phase 2) ↓ html ↑ card ↓ container ↑ container ↓ card ↑ html button ← TARGET document

Memory trick: Capturing = down. Bubbling = up. By default, handlers run in the bubbling phase.

What

When you click a button inside a card, the click doesn't only hit the button. It travels down from the document to the target (capturing), fires on the target, then up from the target back to the document (bubbling). A listener on the card still fires when the button is clicked — because the event bubbles up through it.

In Synora

Synora relies on bubbling: it puts one listener on a container and lets clicks from child buttons bubble up to it (see delegation, next). It also uses event.stopPropagation/closest checks to close menus on outside clicks.

Honest scope — capturingSynora does not register any explicit capture-phase listeners — addEventListener(..., true) / {capture:true} appears zero times in the code. Explain capturing as a concept; say clearly “we use bubbling, not explicit capturing.” This is the one syllabus item to flag as concept-only.
Viva

Q: bubbling vs capturing?
A: Bubbling propagates from the target up to ancestors; capturing propagates from the ancestors down to the target. Handlers default to bubbling.

Q: Does Synora use capturing?
A: No — we use the default bubbling phase; capturing is a concept we understand but didn't need.

Revise: Capturing = down (root→target). Bubbling = up (target→root), the default. Synora uses bubbling; no explicit capture in the code.

Event delegation

One listener for many children — Synora's real pattern.

Container listener + closest() Synora uses this
What

Instead of adding a listener to every button, add one listener to their shared container. When a child is clicked, the event bubbles up; the handler checks event.target.closest(selector) to find which child was hit. Fewer listeners, and it keeps working when rows are added or removed.

Visual
Without delegation: With delegation: button 1 → own listener container → ONE listener button 2 → own listener ↓ closest("[data-del]") button 3 → own listener detect which child was clicked
In Synora

This is genuinely how Synora wires task rows — one listener on the list, closest() decides toggle vs edit vs delete (delegation via .closest() appears ~28×):

jsfrom Synora · scripts/tasks.js
function wireList(container, rerender) {
  container.addEventListener("click", function (e) {
    var toggle = e.target.closest("[data-toggle]");
    var edit   = e.target.closest("[data-edit]");
    var del    = e.target.closest("[data-del]");
    if (toggle)    { toggleComplete(toggle.getAttribute("data-toggle")); rerender(); }
    else if (edit) { openForm(get(edit.getAttribute("data-edit")), rerender); }
    else if (del)  { /* confirm, then remove + rerender */ }
  });
}
Why it matters

Task rows are created and destroyed as you add/complete/delete. Binding a listener to each new row is fragile and leaks; delegating to the surviving container “just works” for rows that don't exist yet. (A real Synora lesson: don't bind listeners inside a function that re-renders its own container — delegate on the wrapper that survives.)

Viva

Q: What is event delegation and why use it?
A: Handling child events with a single listener on a parent, using event.target.closest(). It scales to many/changing children and avoids re-binding after re-renders.

Q: What makes delegation possible?
A: Event bubbling — the child's event reaches the parent listener.

Revise: Delegation = one listener on the parent + e.target.closest() to find the child. Synora wires task rows exactly this way. Relies on bubbling.

DOM performance basics

Keeping DOM work cheap.

jsfrom Synora · scripts/storage.js
function readJSON(key, fallback) {
  try {
    var raw = localStorage.getItem(key);
    if (raw === null) return fallback;
    return JSON.parse(raw);
  } catch (err) {
    console.warn("Synora: could not parse", key, err);
    return fallback;                       // corrupt value → safe default
  }
}
function writeJSON(key, value) {
  try { localStorage.setItem(key, JSON.stringify(value)); return true; }
  catch (err) { console.error("Synora: could not save", key, err); return false; }
}

Keys are namespaced: globals are synora-users, synora-session, synora-theme; per-user collections are synora:<username>:<collection> (e.g. synora:arsh2309:subjects). That namespacing is why one browser can hold several accounts side by side.

Why it matters

No server means no login round-trips, no hosting cost, instant reads, and full offline use — the right trade for a student project. The cost: data is per-device and not shared between browsers (see limitations).

Attendance & CGPA logic

The two formulas the panel will ask you to explain.

The maths, from the real code
Attendance
attendance % = attended ÷ held × 100

Attendance rows store counts only (held, attended); the percentage is derived on read, never stored. Guards: held = 0 means “nothing recorded” → 0%, never NaN; attended is clamped to 0…held.

jsfrom Synora · scripts/app.js
pct: total ? (attended / total) * 100 : 0    // held === 0 → 0%, not NaN

Derived helpers you can mention: how many classes you can still miss and stay above target, and how many you must attend to climb back to it.

CGPA
CGPA = Σ(credits × grade point) ÷ Σ(credits)

A single 10-point system: O=10, A+=9, A=8, B+=7, B=6; failing grades E1/E2/E3 score 0 points but still contribute their credits (a documented assumption — a backlog drags the average). Credits come from the subject record; the grade from the CGPA row.

jsfrom Synora · scripts/app.js
(data.subjects || []).forEach(function (row) {
  var subject = store.subjects.byId(row.subjectId);
  var credits = Number(subject.credits);
  var point   = gradePoint(row.grade);
  if (credits > 0 && point !== undefined) {
    totalCredits += credits;
    weighted    += credits * point;
  }
});
return { value: weighted / totalCredits };   // null if nothing gradeable
Why they're separate systems

Attendance tracking is per-subject and optional (trackAttendance); CGPA counts every graded subject regardless. A subject with attendance turned off still has credits and a grade — so the two never share a filter.

Viva

Q: How is attendance calculated?
A: attended ÷ held × 100, derived from stored counts; held = 0 shows 0%.

Q: How is CGPA weighted?
A: Σ(credits × grade point) ÷ Σ(credits); fails score 0 points but keep their credits.

Q: Why are CGPA and attendance separate?
A: Attendance is optional per subject; CGPA always counts every graded subject — different scopes, so we keep them independent.

Revise: Attendance % = attended/held×100 (counts stored, % derived). CGPA = Σ(credits×point)/Σ(credits); fails = 0 pts, keep credits. Independent systems.

“Why did you use this?”

The panel's favourite question. One honest reason each.

Why HTML?

To give the page structure and meaning — the skeleton everything else builds on.

Why semantic tags?

Meaning + maintainability + accessibility; the markup documents itself.

Why CSS?

To control presentation and layout, kept separate from structure.

Why custom properties?

Consistency and theming — define a colour once, re-theme by swapping token values.

Why Flexbox?

One-dimensional alignment — navbars, button rows, card headers.

Why Grid?

Two-dimensional layout — dashboard decks, calendar, timetable.

Why JavaScript?

Interaction and logic — everything that responds or calculates.

Why DOM manipulation?

To change the interface at runtime without reloading the page.

Why addEventListener?

To respond to user events — clicks, submits, input.

Why event delegation?

One listener handles many (and future) rows; survives re-renders.

Why localStorage?

Client-side persistence with no backend — instant, offline, free.

Why responsive design?

Students use laptops and phones; the layout must work on both.

Why no backend?

Scope: a front-end fundamentals project. localStorage removes server complexity.

Why no React?

To show the core web platform directly — the syllabus is HTML/CSS/JS, not a framework.

Why a demo account?

So a first-time viewer sees a populated, realistic app immediately.

Difference between…

Quick two-line contrasts — a viva staple.

PairDifference
HTML vs CSSHTML = structure/meaning; CSS = presentation/layout.

block vs inlineblock starts a new line and takes full width; inline flows within a line.

✕
“CSS makes the website work.” → “CSS controls presentation and layout.”
✕
“The DOM is the HTML.” → “The DOM is the browser's live object representation of the HTML.”
✕
“localStorage is a database.” → “localStorage is browser-side key–value string storage.”
✕
“Flexbox is for websites.” → “Flexbox is a one-dimensional layout model.”
✕
“Grid and Flexbox are the same.” → “Grid is two-dimensional; Flexbox is one-dimensional.”
✕
“We used event capturing everywhere.” → “We use bubbling and delegation; capturing is a concept we didn't need.”

✕
“== and === are the same.” → “=== also checks type; == coerces. We prefer ===.”
